# Besu EIP-7702 requested-reply Java heap OOM

This repository preserves the sender source, network manifest, and run scripts from a validated Besu 26.11.0 Java **heap** out-of-memory reproduction on a **private** Ethereum testnet. The files are the previously run harness, without a new test method or another OOM trial.

## Where the allocation happens

The issue is in the handling of a **requested pooled-transaction reply**, before the transaction is accepted into Besu's pool. A reply can contain the expected single outer EIP-7702 transaction while that transaction contains a very large *nested* authorization list. The outer count and network-message-size checks do not impose a practical count bound on the nested objects created by decoding it. The links below are pinned to Besu 26.11.0 ([source revision](https://github.com/besu-eth/besu/tree/0e595f9eaf4b760ee7069fcdf8d901685f1641eb)).

1. **Request and initial response decode.** [`GetPooledTransactionsFromPeerTask.processResponse`, lines 93–100](https://github.com/besu-eth/besu/blob/26.11.0/ethereum/eth/src/main/java/org/hyperledger/besu/ethereum/eth/manager/peertask/task/GetPooledTransactionsFromPeerTask.java#L93-L100), calls `transactions(hashes.size())`. Its comparison of the decoded transaction with the peer's announced type and size follows at [lines 102–126](https://github.com/besu-eth/besu/blob/26.11.0/ethereum/eth/src/main/java/org/hyperledger/besu/ethereum/eth/manager/peertask/task/GetPooledTransactionsFromPeerTask.java#L102-L126). Those comparisons therefore cannot avoid the memory spent decoding this reply.
2. **Outer-list guard.** [`PooledTransactionsMessage.transactions`, lines 79–92](https://github.com/besu-eth/besu/blob/26.11.0/ethereum/eth/src/main/java/org/hyperledger/besu/ethereum/eth/messages/PooledTransactionsMessage.java#L79-L92), passes the number of requested hashes as `maxTransactions` to the RLP reader. That guards the number of *transactions in the reply*. A reply with one requested outer transaction passes it regardless of the number of authorizations inside that transaction.
3. **Nested-list materialization.** [`CodeDelegationTransactionDecoder.decode`, line 69](https://github.com/besu-eth/besu/blob/26.11.0/ethereum/core/src/main/java/org/hyperledger/besu/ethereum/core/encoding/CodeDelegationTransactionDecoder.java#L69), calls the one-argument `readList` for `codeDelegations`. [`RLPInput.readList`, lines 418–448](https://github.com/besu-eth/besu/blob/26.11.0/ethereum/rlp/src/main/java/org/hyperledger/besu/ethereum/rlp/RLPInput.java#L418-L448), gives that overload an `Integer.MAX_VALUE` element ceiling, allocates a list sized to the encoded element count, and decodes each entry. The [entry decoder, lines 83–100](https://github.com/besu-eth/besu/blob/26.11.0/ethereum/core/src/main/java/org/hyperledger/besu/ethereum/core/encoding/CodeDelegationTransactionDecoder.java#L83-L100), creates the authorization's fields and a `CodeDelegation` object. The bytes occupied by an encoded entry and the heap used by its decoded objects are different quantities.
4. **Message cap.** Besu's [default ETH message cap is 10 MiB](https://github.com/besu-eth/besu/blob/26.11.0/ethereum/eth/src/main/java/org/hyperledger/besu/ethereum/eth/EthProtocolConfiguration.java#L24-L32). The tested reply is below that byte cap. It still creates enough nested objects across requested replies to exhaust the tested Java heap. A byte cap limits wire input; it does not by itself cap this nested allocation.

This identifies the missing bound at the **nested authorization-list level** in the tested decode path. A possible mitigation would check a defensible nested count or resource budget before allocating and decoding the entries. The record here establishes the tested failure, not which mitigation Besu should adopt.

## Comparison with Nethermind and Geth

**Nethermind has a direct nested-list guard in the inspected source revision.** Its [`SetCodeTxDecoder`, lines 12–23](https://github.com/NethermindEth/nethermind/blob/24d803cedd24733667666512b74de00408b3c9f9/src/Nethermind/Nethermind.Serialization.Rlp/TxDecoders/SetCodeTxDecoder.cs#L12-L23), supplies an `AuthorizationListLimit` to the decoder, derived from the configured maximum block gas and the base gas cost per authorization. Its [`RlpReader.DecodeNonNullArray`, lines 582–600](https://github.com/NethermindEth/nethermind/blob/24d803cedd24733667666512b74de00408b3c9f9/src/Nethermind/Nethermind.Serialization.Rlp/RlpReader.cs#L582-L600), counts entries and checks that limit **before** allocating the array or decoding authorization objects. That is the kind of nested bound missing from the inspected Besu path. This is a static source comparison, not a Nethermind runtime test or a claim of blanket immunity.

**Geth differs in when it materializes the outer reply.** In v1.17.6, Geth declares the pooled reply's outer list as [`rlp.RawList[*types.Transaction]`](https://github.com/ethereum/go-ethereum/blob/v1.17.6/eth/protocols/eth/protocol.go#L281-L288). Its [`RawList.DecodeRLP`](https://github.com/ethereum/go-ethereum/blob/v1.17.6/rlp/raw.go#L80-L113) keeps the list in encoded form and counts its outer items; decoding those items into transaction objects is a separate operation. In [`handlePooledTransactions`](https://github.com/ethereum/go-ethereum/blob/v1.17.6/eth/protocols/eth/handlers.go#L655-L675), Geth checks whether transactions are accepted and calls the request tracker with the reply ID and outer count before handing the packet to the backend.

That ordering can avoid transaction-object decoding for replies rejected at the request-tracking stage. Besu's path above creates the transaction and its nested authorizations before its later announcement checks. This is a concrete difference in when the two clients materialize **outer reply contents**; it is **not** evidence that Geth rejects, safely handles, or is immune to the tested nested authorization input. No equivalent Geth runtime OOM claim is made here.

Besu's [earlier public outer-list fix](https://github.com/besu-eth/besu/commit/2d2d8f9a8b3f81d5d310af9f0da49d2c297bc316) addresses a related decode-before-count problem for *many outer transactions*. This reproduction uses one requested outer transaction with many nested entries. That overlap matters for prior art; novelty and credit remain unresolved.

## Result and boundary

On a 32 GB Linux host, the unmodified Besu 26.11.0 image selected an 8,417,968,128-byte maximum Java heap (about 7.84 GiB). After 15 established ETH/71 peers delivered seven waves of Besu-requested `PooledTransactions` replies (105 replies total), Besu logged `java.lang.OutOfMemoryError: Java heap space` and exited with code 3. Docker reported `OOMKilled=false` and no container memory limit. The matched 105-reply control, using one EIP-7702 authorization per reply, stayed healthy. [The validated observations](evidence/validated-32g.md) distinguish this process exit from host or container memory exhaustion.

This supports the tested 8 GB heap configuration, which matches [Besu's published maximum-heap recommendation for hosts with at least 24 GB RAM](https://docs.besu-eth.org/public-networks/how-to/configure-java/manage-memory). It does not show that every Besu node crashes. On a separate 64 GB host, the same primitive and 105, 120, and 135 requested replies **did not** cause a process exit with a 16 GiB heap, although they caused high transient heap use. A populated public-network peer table and public-network delivery probability were not tested.

## What happens before validation

The sender opens ordinary RLPx/ETH/71 sessions and completes Besu's chain-head peer validation. Each peer advertises one type-4 (EIP-7702) transaction. The sender waits for Besu's matching `GetPooledTransactions` request, then returns one outer transaction. The response is 9,720,054 decoded RLP bytes, below Besu's default 10 MiB ETH message cap, but contains 360,000 nested authorization entries. The transaction is intentionally invalid for eventual pool admission; the observed cost occurs during decoding, before that decision. No victim RPC or Engine API call delivers the input.

At the pinned Besu 26.11.0 source revision, [`PeerTransactionTracker`](https://github.com/besu-eth/besu/blob/26.11.0/ethereum/eth/src/main/java/org/hyperledger/besu/ethereum/eth/transactions/PeerTransactionTracker.java#L224-L238) can request the first announced transaction while its accumulated size budget is still zero. The step-by-step decode path and client comparison are above.

## Reproduce on a private host

Use a disposable **Linux x86-64 host with at least 32 GB RAM**, Docker, `git`, Go **1.27.3**, `jq`, `curl`, Python 3, `sha256sum`, `sudo iptables-legacy`, and [Kurtosis CLI 1.22.2](https://docs.kurtosis.com/install). The historical scripts require non-interactive `sudo` for one private bridge rule, and their paths assume `/tmp/vec-besu-32g-20261022`. They check that the enode uses the private `172.16.*` enclave network; the sender also rejects public IPs. The pinned Besu image and unchanged JVM defaults are in [`network_params.yaml`](network_params.yaml).

Start with [the historical runbook](RUNBOOK.md). It stages the exact [`sender/`](sender/) and [`harness/`](harness/) files into the paths expected by the scripts, builds the sender against pinned Geth, then runs a one-peer admission preflight, a fresh 15-peer benign control, and a fresh 15-peer larger-input trial. Each full run collects sender, peer admission, JVM, Docker, Besu, and Lighthouse observations. A failed sender, inactive-peer gate, or devnet launch is an **inconclusive setup failure**, not a negative vulnerability result. The runbook describes how to inspect the Java heap OOM and clean up each private enclave.

The scripts retain their historical absolute paths and Linux bridge assumptions so readers can see exactly what was validated. The repository does not claim that the documented restaging has been rerun on another machine. Any different JVM maximum, changed peer admission, or altered private network should be described as a new trial rather than the historical result.

## Limits and related work

- The demonstration uses 15 **established** private peers on a short chain with an otherwise empty peer table. It does not establish how often an attacker can obtain 15 slots on a populated public node.
- The large transaction is rejected after parsing. The issue is pre-admission allocation, not accepted on-chain state or fee economics.
- The observed failure is a JVM heap OOM and process exit, not exhaustion of all 32 GB host RAM or a Docker memory-limit kill.
- The result depends on the tested version and heap ceiling. The separate 16 GiB non-OOM trials bound what this evidence can claim.
- Public prior art includes Besu's [outer-list decode cap](https://github.com/besu-eth/besu/commit/2d2d8f9a8b3f81d5d310af9f0da49d2c297bc316), [EIP-7702 pool memory accounting](https://github.com/besu-eth/besu/pull/7984), and [authorization allocation work](https://github.com/besu-eth/besu/pull/11866). None was identified as a public report of this exact nested-list heap OOM, but private duplicates cannot be ruled out.

Only run this repository on infrastructure you own or have explicit permission to test. It does not contact public Ethereum peers.
